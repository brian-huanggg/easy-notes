# Localization

Supported: `zh-Hant` (Traditional Chinese) and `en` (English (US)). **The source language is zh-Hant**: the Chinese written in code is the key and `en` is the translation. Repository documentation, code comments, scripts and commit messages are always en-US; only user-facing strings follow this document.

## Language selection

- Defaults to the system language; an unsupported system language falls back to English (`CFBundleDevelopmentRegion = en`, `CFBundleLocalizations = [zh-Hant, en]`).
- iOS / iPadOS: use the system "Settings > EasyNotes > Language"; there is no in-app picker (Apple's standard approach, one less UI to maintain).
- macOS: Settings (⌘,) offers a language option written to `AppleLanguages` in `UserDefaults`, **taking effect after a restart**; "Follow system" removes `AppleLanguages` and the app's own `AppLanguageOverride` flag.
- No live switching: `String(localized:)` and AppKit menus resolve to strings at creation, so switching live would mean swapping bundles and rebuilding every screen and WebView for a rarely used feature.

## String resources

Each module that has user-facing text ships its own `Localizable.xcstrings` (String Catalog): App, `EasyNotesCore`, `EasyNotesUI`, `ExcalidrawKit`, each plugin, and `Flashcards`.

- A plugin's strings live in the plugin and go away with it, which also fits "Core knows no plugins". Core and EasyNotesUI are two targets of one package, each with its own catalog.
- The file sits at the target root (`Sources/<Target>/Localizable.xcstrings`); `Package.swift` sets `defaultLocalization: "zh-Hant"` and `resources: [.process("Localizable.xcstrings")]`.
- The key is the zh-Hant source text. Reasons: the compiler extracts it straight from code, no separate key scheme is needed, and the zh-Hant UI is identical to having no localization. A key with interpolation is extracted as `%lld documents`-style placeholders (`%lld`, `%@`).
- When the same Chinese phrase needs different English in different contexts, write the Chinese source differently instead of distinguishing with a comment; comments are only background for translators.

## Code conventions

Literals in `Text("…")` and `Button("…")` look up the **main bundle** by default and do not find a package's own catalog (a literal converted to `LocalizedStringResource` has the same problem). So each module has an `L(_:)` that binds the literal to its own bundle:

```swift
// <Target>/Localization.swift (one per module; #bundle must expand in that module, so it cannot be shared)
func L(_ value: String.LocalizationValue) -> String {
    String(localized: value, bundle: #bundle)
}
```

`L` returns a resolved `String`, so it works anywhere a `String` is accepted and component APIs need no type change. Because there is no live switching, strings are resolved at the call site and the deferred resolution of `LocalizedStringResource` is not needed.

| Situation | Form |
| --- | --- |
| SwiftUI text, buttons, titles, `help` | `Text(L("<zh-Hant text>"))`, `Button(L("<zh-Hant text>"))`, `.help(L("<zh-Hant text>"))` |
| Interpolation | `L("\(count) <zh-Hant text>")`; never build a `String` first and pass it in |
| Component APIs, return values, error messages | Also `L("…")`; the parameter type stays `String` |
| Plurals | Add plural variations for the key in the catalog (`en` needs one / other) |
| Dates, numbers, relative time | Use `Date.formatted`, `RelativeDateTimeFormatter`, `Intl.*`; never assemble by hand; never hardcode `Locale(identifier: "zh-Hant")` |
| Strings users never see | Logs, `precondition` messages and `#Preview` sample data are not translated |

`L(…)`'s parameter type is `String.LocalizationValue`, which the compiler recognizes, so extraction yields the right key and interpolation. **New code never writes Chinese literals that do not go through `L(…)`**; `scripts/check-l10n.py` checks that Chinese literals go through `L(…)`, that each `L(…)` key has an English entry in the module's catalog (state `translated`), and that web `t(…)` keys have a matching entry in the `en` dictionary of `i18n.ts`; `--stale` additionally lists keys the code no longer uses.

## Strings that do not change with language

These strings are data or protocol; changing them with language would make one vault behave differently on devices set to different languages. They are collected into constants and the line ends with `// l10n:fixed` to tell the check script it is deliberate.

| String | Reason |
| --- | --- |
| Folder and file name conventions: `Attachments/` (the legacy `附件/` is read-only), `.easynotes/`, `CLAUDE.md` | Paths are referenced by links, synced across devices and read by Claude Code |
| Conflict-copy file name `<name> (衝突 <device> <date>).<extension>` | Generated by the sync engine; the app recognizes it by prefix and syncs it across devices, so two devices in different languages must recognize the same form |
| Text inside file formats: frontmatter keys, card syntax, fields of `.excalidraw` / `.pdf.ink` / `.jsonl` | Open formats other tools read |
| Content of the vault's `CLAUDE.md` (always English) | Read by Claude Code; created only when the file does not exist, and if it followed the UI language two devices in different languages would each create different content and produce a conflict copy. Examples inside (card syntax, paths) are English too, with the attachment path written `Attachments/` |

**Defaults generated at creation time** use the UI language at that moment and are the user's files afterwards, never rewritten: default names of new files ("Untitled", "Whiteboard"), new folders, pasted image file names, and first-launch sample content (`Seed` picks the Chinese or English version by `Bundle.main.preferredLocalizations`, each language with its own set of file names and link targets).

## Display text in the index

The `summary` from `DocumentKind.index()` ("123 words", "N pages", "N elements") is display text that Core stores but never interprets, so its content carries the UI language at generation time. The index records the language it was generated in; when it differs from the current one the whole index is rebuilt (the index is rebuildable anyway and language switches are rare). Titles, full text and links are unaffected by language. The language is folded into the index signature (compared in the same place as contributor versions) and Core only compares strings.

## WebView plugins

- When creating `WebEditorHost`, Swift passes the language identifier to JS as a one-time parameter, not on the typing path.
- JS strings are collected in `web/src/shared/i18n.ts`: `t(key, params)`, with the key again being the zh-Hant source and a miss returning the key; one dictionary per language.
- Relative time, numbers and dates use `Intl.RelativeTimeFormat` / `Intl.NumberFormat` / `Intl.DateTimeFormat`; never assemble "N minutes ago" by hand.
- Data passed into JS contains no translated text; JS composes it by language (for example Swift passes a `modified` timestamp and JS builds "updated N minutes ago").

## Verification

- `scripts/check-l10n.py`: lists Chinese literals that neither go through `L(…)` / `t(…)` nor carry `// l10n:fixed`; run before committing.
- The Xcode scheme's Double-Length Pseudolanguage checks for layout breakage; Right-to-Left Pseudolanguage checks leading / trailing usage.
- Any `en` catalog entry whose state is not `translated` is a missing translation.
